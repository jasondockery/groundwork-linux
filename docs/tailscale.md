# Tailscale on Linux

Read the [shared Tailscale guide](https://github.com/jasondockery/groundwork-core/blob/main/docs/tailscale.md) for policy, MagicDNS, MFA, device approval, expiry, platform capabilities, and two-way checks. This page owns Linux setup only; Omarchy has its own repo and Arch service steps.

Where Homebrew is present, the shared Groundwork engine installs the Tailscale formula. For that installation, start the service with `sudo "$(command -v brew)" services start tailscale`, then sign in locally with `sudo "$(command -v tailscale)" up --timeout=5m` and approve the device. Resolving those executables before `sudo` preserves Homebrew's location when root has a different PATH. If another supported package source already owns `tailscaled`, use that service instead of starting a duplicate daemon.

Headless and ARM64 Ubuntu setups can skip Homebrew entirely. On those hosts, install the stable native package using the [official instructions for your distribution and release](https://pkgs.tailscale.com/stable/) first; the shared engine does not install that package automatically. On Ubuntu with systemd, run `sudo systemctl enable --now tailscaled`, then `sudo tailscale up --timeout=5m` and complete local device approval. Use the native package manager for updates. These are host-service steps, not development-container setup. WSL normally uses the Windows host's Tailscale installation; see [groundwork-windows](https://github.com/jasondockery/groundwork-windows/blob/main/docs/tailscale.md) before enrolling a WSL distribution separately.

After reviewing the shared owner-scoped network and SSH policy, enable inbound Tailscale SSH with `sudo "$(command -v tailscale)" set --ssh`. Check `tailscale status`. From another approved machine, substitute its local login and MagicDNS name in `ssh LOCAL_USER@MACHINE`; confirm the remote hostname and attach to tmux or Herdr. Test the reverse direction separately.

Keep agent web interfaces on loopback and use SSH forwarding when needed. Do not advertise routes, enable Funnel, open public ports, or insert static DNS entries for ordinary personal access. Package/service presence is not proof of sign-in or cross-machine acceptance.

## Desktop access

On a real GNOME desktop, the shared engine prepares `groundwork-remote-desktop` during a desktop apply. This uses the native GNOME RDP service rather than applying Omarchy or installing a second desktop. If the distribution does not already include them, install its `gnome-remote-desktop` and GNOME Settings packages first. On Ubuntu/Debian GNOME, that is `sudo apt install gnome-remote-desktop gnome-control-center`. Other distributions retain their native package manager; other desktops need their own supported server.

Run `groundwork-remote-desktop` in the logged-in desktop, then use Settings → System → Remote Desktop → Desktop Sharing. Enable sharing/control and choose its local credentials. GNOME owns their keyring storage and certificate; they are never copied into Groundwork. Once RDP is configured, a subsequent `chezmoi apply` enables/starts the native user service without resetting those credentials. Check `systemctl --user status gnome-remote-desktop.service`; native startup and a visible sharing setting are not proof of a working remote session.

Connect using Windows App on macOS, or another supported RDP client, using the destination's MagicDNS name and actual port shown by GNOME (commonly 3389 or 3390). Verify its certificate and use the sharing credentials, which may differ from the local login. Add only the chosen port to the [shared owner-scoped grant](https://github.com/jasondockery/groundwork-core/blob/main/docs/tailscale.md#agent-tools-and-screens). A host firewall must allow that port on the Tailscale interface; tailnet grants do not filter LAN traffic or override a broader host allow rule.

Verify screen/control from a second approved computer and again after reboot/login. Desktop Sharing shares the existing logged-in session; it does not promise pre-login/headless access, disk unlock, or wake from power-off. Use native Settings to disable sharing when no longer needed. Headless machines, containers and WSL are excluded from the engine's desktop hook; use terminal access or the Windows host's own setup instead. For Apple Silicon Omarchy, use its dedicated repository's automatic WayVNC service and a VNC client such as macOS Screen Sharing.
